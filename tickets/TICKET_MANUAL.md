## 3. 수신함(MSG) 읽는 법 ✅

한 줄 = 메시지 1건. 같은 티켓번호가 여러 줄이면 **맨 위(최신) 한 줄만** 보면 된다. 티켓에 들어가면 이전 업데이트가 전부 있다.

**글자색**
- 노랑 = 내가 아직 안 연 것 (새 것)
- 회색 = 한 번 클릭해 본 것

**보낸 사람 앞 점** (상대방 상태)
- 초록 = 접속 중 / 노랑 = 자리비움 / 빨강 = 로그아웃, 터미널 안 쓰는 사람, 또는 자동 알림

**메시지 종류 (제목으로 구분)**

| 제목 패턴 | 의미 | 할 일 |
|---|---|---|
| `SCHD SDSK 번호 has been assigned to you.` | 나에게 새로 배정 | 내용 확인, 정리 목록에 추가 |
| `*SDSK *HELPDESK / ALERT: ... was distributed and assigned to you` | **헬프데스크 자동 배정** | 국가 확인 → 한국 아니면 재배정 대상 (5-2) |
| `User note added` / `replied to your note` | 새 글 | 최신 글 읽기, 정리 갱신 |
| `Summary was updated` / `Lock Rep was updated` / `has been re-assigned` | 변경/재배정 | 담당(Rep) 바뀌었는지 확인 |
| `deferred` | 보류됨 | 마감일(보류 날짜) 갱신 |
| `Sdsk Advisory / REMINDER for not updated SDSK tickets` | 업데이트 안 한 티켓 경고 | 알림 대상 |
| `INSTANT BLOOMBERG: ...` | 채팅 내용 | 채팅 업무 |
| `Daily Listing Of Appointments`, `Daybreak Alert` | 일정/뉴스 | 무시 (일정은 필요 시 참고) |

**새 알림이 뜨는 방식**
- 근무 중 새 티켓/메일이 오면 우상단에 알림(`Msg:S. Notificat…`)이 뜬다. 클릭하면 수신함이 열리고 새 것들을 한 번에 볼 수 있다. ✅
- 터미널이 꺼져 있던 동안(퇴근 후) 온 것은 알림이 안 뜬다 → **출근 후 터미널을 처음 켰을 때 수신함에서 노란색(안 읽은) 것을 직접 확인**해야 한다. ✅
- 자동화 방침: **새 알림창이 뜰 때만** 확인한다 (사용자 결정 2026-10-09). 단, 아침 첫 실행 때는 밀린 노란색을 한 번 훑는 단계가 필요 ⚠️(미결정, 11장).

## 4. 티켓 화면 구조 ✅

수신함 메일의 파란 링크 `블룸버그 기능 (SDSK)` 클릭 → 티켓으로 들어간다.

- **Summary** = 제목, **Rep** = 책임자, **Status**, **Employee**, **Progress**
- 오른쪽 **Additional Information**: Due Date(칸이 있음, 비어 있을 때가 많음), Global Region, **Country, Office** (할당 국가). 보통 이 나라 사람이 Rep.
  - 수출입은 보내는 쪽 → 배송 후 받는 쪽이 Rep가 된다.
- 가운데 **Key Details**: 글이 1, 2, 3 … 순서로 쌓인다. **1번 = 티켓 전체 설명(꼭 읽기)**, 맨 아래 = 최신 글.
  - 오더 연결 티켓은 1번 글에 보낼 물건, 유저 이름/전화번호가 있다. 전화가 안 될 때가 있고, 스크롤을 내리면 관련자가 **새 전화번호/주소**를 따로 줄 수 있다. **가장 최근 글이 가장 믿을 만하다.** (예: 17번 글의 ship to 주소, contact name/phone/email → workbench에 반영)
- 위쪽 버튼: **Add Note**(글 쓰기), **Resolve**(Rep가 일 끝나면), **Defer**(Rep가 지연시킬 때), Withdraw, Transfer
- 왼쪽: Attached(첨부 업/다운), **Subscribers**(참고자), **Add'l Reps**(함께 일하는 사람)
  - 내게 메시지가 온다 = 나는 Subscriber 또는 Add'l Rep 중 하나. 참고자 = Subscriber, 일에 참여 = Rep.

## 5. 업무 규칙

### 5-1. 정리 대상 ✅ (사용자 결정 2026-10-09)
- **진행 중인 것만** (목록에서 주황색). 회색(마감)은 대상 아님.
  - 단, 회색인데 Resolve 안 된 것 / 내가 깜빡한 것이 있을 수 있어 Rep 목록의 마감 건은 가끔 점검할 가치가 있음 ⚠️
- **Rep와 Subscriber가 겹치면 Rep로 분류.** 두 구분을 나눠서 정리한다.
- 티켓 제목에 STO/OBD/ORD 번호가 있으면 workbench 오더 행과 연결.

### 5-2. 재배정 규칙 ✅ (실행은 ⛔ 미구현, 급하지 않음)
티켓의 **Country/Office**를 본다.

| 티켓 국가/사무실 | 처리 |
|---|---|
| Korea | 내가 그대로 처리 |
| Shanghai | **Jackie Guo**에게 배정 |
| Beijing | **Tom Wang**에게 배정 |
| 그 외 나라 | **9) Unlock** (스스로 빠지기) |

조작 순서: 티켓 화면 `99) Options` → `12) Assign to Rep` → 담당자 이름 입력 → `1) Assign`. (Unlock은 같은 메뉴의 `9) Unlock/Send to Distribution`)

> ⚠️ **실행 전 반드시 사용자에게 확인**받는다. 잘못되면 되돌리기 난감함. (자동 실행 금지)

### 5-3. 마감일(확인 날짜) 정하는 법 ✅ (사용자 결정 2026-10-09)
티켓 **내용을 읽고** 아래 우선순위로 적는다.

1. **본문에 누가 "언제까지 해달라"고 쓴 날짜 / Due date 언급**이 있으면 그것 (최우선)
2. 없으면 **가장 마지막 Defer 날짜** (`deferred until ...`)
3. 둘 다 없으면 **"확인필요"** 라고 적는다 (날짜를 지어내지 않는다)

참고: 티켓 화면에 `Due Date` 칸, `Next Action Date` 칸이 따로 있다. 이 값들을 어떻게 취급할지는 11장 미결.

### 5-4. 표기 규칙 ✅ (사용자 지시 2026-10-09)

**티켓번호는 항상 `SDSK 숫자` 형식**으로 저장·표시한다. (숫자만 쓰지 않는다. 예: `SDSK 1333118325`) 상태 저장소의 키도 이 형식.

**"상황" 칸은 줄글 금지.** 짧게, 줄바꿈으로 나눠서, **내가 필요한 정보만** 적는다.
- 한 줄 = 한 사실. 문장으로 이어 쓰지 않는다.
- 사람 이름 + 결과를 짧게: `유저 Geon Choi 연락 안 됨 (10/2, 10/6~8)`
- 목록이 있으면 항목별로 줄바꿈해서 나열: `Himchan이 준 대체 번호 4개:` 다음 줄부터 `이름 번호` 한 줄씩
- 내가 해야 할 일은 따로 한 줄로 분리: `→ 키보드 4개 배송 필요`
- 날짜는 `10/9` 형태로 짧게

예시
```
SDSK 1334533923 | Add-On Non-Billable SID(s)
상황
 유저 Geon Choi 연락 안 됨 (10/2, 10/6~8)
 Himchan이 준 대체 번호 4개:
  Hyunbin Ahn +82-2-3276-5910
  Geonu Kim +82-2-3276-6161
  Geon Choi +82-2-6390-3226
  Injun Hwang +82-2-3276-5598
 → 키보드 4개 배송 필요
확인 날짜: 10/14 (defer)
```

### 5-5. 본문 스크리닝 규칙 ✅ (사용자가 가장 중요하다고 강조)

**티켓 본문을 직접 읽어서(스크리닝) 필요한 정보를 뽑는 것이 핵심이다.** "터미널 글자를 프로그램이 복사해 읽지 못한다"는 것은 기술적 한계일 뿐, **화면을 캡처해서 내가(Claude) 읽는 것은 된다**(시험 실행에서 실제로 읽음). AI Summary는 보조 도구일 뿐 본문 읽기를 대신하지 않는다.

- **처음 보는 티켓**: 1번 글(전체 설명)부터 맨 아래 최신 글까지 **전부** 스크롤하며 읽는다. 마감일 언급, 요청 사항, 전화번호/주소 변경, 내가 해야 할 일을 찾는다.
- **이미 정리한 티켓**: 저장해 둔 "마지막으로 읽은 글 번호" 이후의 **새 글만** 읽는다. (글 번호는 화면에 `13. NAME 날짜` 형태로 보임)
- AI Summary는 전체 흐름 파악용으로 참고하되, `Summarized up to:` 이후의 글과 날짜/연락처는 반드시 본문에서 확인한다. 요약과 본문이 다르면 본문을 믿는다.
- 가장 최근 글이 가장 믿을 만한 정보다 (주소/연락처가 중간에 바뀌는 경우).
- 시험 실행(2026-10-09)에서는 비용을 아끼려고 AI Summary + 최신 글 위주로만 읽었다 → 정식 운영은 위 규칙대로 본문 전체 스크리닝으로 한다. (긴 티켓은 글이 50개 넘기도 해서 시간이 걸린다. 그래서 "마지막 읽은 글 번호"를 저장해 두 번째부터는 새 글만 읽게 한다.)

### 5-6. 티켓 ↔ 오더 연결 규칙 ✅ 방향 확정 / ⚠ 세부는 시안 개선 중 (2026-10-09)

**배경 ✅**: 티켓만 있다가 일이 진행되면서 ZOR/ZRX/ZRE 같은 오더가 생기기도 하고, 반대로 오더가 먼저 있고 티켓이 나중에 오기도 한다. 둘은 같은 내용을 공유하므로 workbench에서 **한 곳(한 표)** 에서 함께 관리한다. 지금 배송 보드에도 오더 밑에 SDSK 번호가 이미 표시되는 오더가 있다(예: ZOR 7853869 ↔ SDSK 1334533923, ZOR 7870784 ↔ SDSK 1338724173, ZRX 67106923 ↔ SDSK 1338871634).

**사용자가 확정한 방향 ✅ (피드백 순서대로)**
1. 오더와 티켓을 **한 표에서 함께** 관리한다. 오더 쪽 칸(Type, 체크, Order #, Item, M/N, S/N, Customer, Phone, Address, Memo)은 **하나도 빼지 않는다.** (오더 정보를 줄여 합친 시안은 "M/N, S/N 등이 너무 빠졌다"며 거부됨)
2. "티켓만 / 오더로 전환 / 확인필요 / 오더 대기 / 연결 후보" 같은 **상태 칸·배지·전환 버튼·후보 상자는 "투머치"라서 쓰지 않는다.** 새로 나온 것은 **`NEW` 표시만** 붙인다.
3. 티켓만 있는 줄도 같은 표의 한 줄이다(Type은 "티켓", Item/M/N/S/N은 비움).

**연결 동작 (코드 설계 메모)**
- **번호가 같으면 말없이 한 줄로 합친다**(`NEW`만 붙음). 번호 비교는 **숫자만** 뽑아서 한다(`STO 4500752901`, `OBD 92192173`, `ORD 28201960`, `ZOR 7870784` 등).
- 매칭 신호: 티켓 제목·본문·Linked 항목(`*ORD 28164224`, `*ADSK ...`) ↔ 오더의 STO/OBD/ORD/ZOR/ZRX/ZRE 번호, 그리고 오더가 이미 가진 SDSK 번호.
- **번호가 안 맞으면 합치지 않고 제안도 하지 않는다.** (고객명만 비슷한 "연결 후보" UI는 사용자가 거부 → 되살리지 말 것)
- **직접 연결**: Order # 칸 아래의 작은 번호 입력칸에 번호를 적고 Enter. **아직 없는 번호도 적어 두면** 나중에 SAP 오더나 티켓이 들어올 때 자동으로 붙는다. (그래서 "오더로 전환/껍데기 오더" 방식은 쓰지 않는다)
- 값 우선순위: 칸에 **SAP 값이 있으면 SAP 값**이 보이고, 비어 있는 칸만 티켓에서 가져온/직접 적은 값이 보인다. 주소·연락처가 티켓 최신 글과 달라도 **자동 반영/알림은 하지 않는다**(사용자가 칸을 눌러 직접 고침).
- **메모는 하나로 합친다**(오더 메모와 티켓 메모를 줄바꿈으로 이어 붙임).
- 1티켓:N오더, 1오더:N티켓 허용(한 줄 안에 목록) — 시안은 1:1만 보여줌.
- 분리(연결 해제)가 필요하면 사용자가 번호 연결을 지울 수 있어야 한다(⚠ 미설계, 시안에 없음).

**⚠ 미결 / 개선 필요**
- 사용자가 최신 시안(시안 8)에 대해 **"디벨롭 필요"** 라고 했다. 구체적으로 무엇이 불만인지는 아직 못 들음 → **다음 세션 첫 질문**.
- 자동 합침이 틀렸을 때 되돌리는 방법(분리 버튼 없이 어떻게?)
- 이 연결 확인을 **SAP 오더 수집 코드의 어느 시점**에 끼워 넣을지 (오더 수집 직후 / 별도 주기 점검)

### 5-7. 티켓 → 배송장 행 작성 규칙 ✅ (사용자 지시 2026-10-12, 첫 사례 SDSK 1339373759 sloc to sloc)

티켓 1번 글(본문)을 읽고, 할 일이 **물건 이동/배송**이면 배송장(workbench 보드)에 한 줄을 만든다.

| 칸 | 채우는 값 |
|---|---|
| Type | 배송 |
| Order # | **`SDSK 숫자`를 오더번호처럼** 넣는다 |
| Item / M/N / S/N | 본문 표의 Material Description / Material / Serial Number |
| Customer | 본문에서 받는 사람·팀으로 지정된 이름 (예: `BOS Team`) |
| Phone | 티켓에 있으면, 없으면 빈칸 (지어내지 않는다) |
| Address | plant 코드로 정한다. **6523 = `Bloomberg Seoul Office (6523)`** (다른 plant는 확인 후 이 표에 추가) |
| Memo | 이동 내용을 `→`로: `6507/0013 → 6523/0016 sloc to sloc` (plant/sloc 출발 → 도착) |

- 만드는 방법: `POST /api/orders/add_manual` (`items.add_manual_note`) — `orderLabel`에 `SDSK 숫자`, `cells=[Item, M/N, S/N, Customer, Phone, Address, Memo]`, `itemType=배송`, `cellCount=7`. 이 방식은 order_no가 빈값이라 Portal/ZREC/POD 자동화가 건드리지 않는다.
- 화살표는 `→` (사용자 지정, `->` 아님). DB 확인 시 콘솔에서 한글이 깨져 보여도 저장값은 정상일 수 있으니 바이트로 확인.
- 쓰기이므로 **내용을 사용자에게 보여주고 확인받은 뒤** 만든다 (첫 사례는 사용자가 구성을 직접 지정).

## 6. 목록 엑셀 내보내기 — 색 구분 문제 ✅

엑셀 파일에는 **색이 안 들어온다** (셀 서식 전부 기본값 — 직접 확인). 대신 **상태 열**로 구분한다.

### 6-1. SUB 목록 (`subs 목록.xlsx`)
- 열: Dept, Opened, Lng, **St**, Pb, VSAT, Gtwy, Cl, Summary, **Rep Name**, Customer, Dur
- **St 값 분포**: `R`(82) / `E`(3) / `A`(2) / `>R`(2) / `W`(2) / `<W`(1)
- 화면에서 주황색이던 5건과 `A`,`E` 5건이 일치 → **진행 중 = St가 `A` 또는 `E`**, 나머지(`R` 해결, `W` 철회, `>R`/`<W`는 R/W 앞의 표시 문자)는 마감 ⚠️ (Legend로 최종 확인 필요)
- **Rep Name이 MINJUNG SUH이면 Rep**(내 담당), 아니면 Subscriber.

> ⚠️ **SUB 내보내기에는 티켓번호(`SDSK 숫자`) 열이 없다** (2026-10-09 확인). 열이 Dept, Opened, St, Summary, Rep Name 뿐이라, 티켓번호는 **Summary(+Opened 날짜)로 수신함/티켓 화면과 맞춰서** 찾아야 한다. 또 **내가 글을 쓴 티켓이 REP/SUB 목록 어디에도 없을 수 있다**(예: `SDSK 1334533923`은 내 글이 있는데 SUB 목록에 해당 행이 없었음). 그래서 수신함이 목록과 별개로 필요한 2번째 소스이다.

### 6-2. REP 계열 (`rep 목록.xlsx`) — ⚠️ 문제
- 이번에 받은 파일은 **MYDB(내 대시보드)** 내보내기였다. 열: Function Name, Dept, Ticket ID, Open Date, Class, Summary, Problem Name, Customer, Region, User Name, Last Updated, Seq (98건)
- **상태 열이 없고, Rep 열도 없다.** (`User Name`은 요청한 직원이지 Rep가 아님) → 진행/마감 구분 불가.
- MYDB는 사용자가 직접 `Add Ticket / Remove` 하는 개인 목록으로 보인다 (이미 Resolved된 1338869627이 Rep가 Tina Wang인데도 들어 있음) ⚠️ → "내가 Rep인 티켓의 정답 목록"으로 쓰면 안 된다.
- **해결안**: `REP`(Search by Owner/Rep) 화면에서 내보내기. SUB 화면과 같은 구조(St, Rep Name 열)일 가능성이 높다 ⚠️ — 샘플 확보 후 확정.

## 7. 자동화 설계

### 7-1. 단계
| 단계 | 내용 | 상태 |
|---|---|---|
| 0 | 조사: 알림창 감지 방법, 엑셀 내보내기 자동화 가능 여부, 화면 글 읽기 방법 | 🔶 알림창/키입력/AI Summary 확인함, 엑셀 내보내기 자동화는 미확인 |

### 7-2. 기술 사실 ✅ (이 PC에서 직접 확인, 2026-10-09)
- 터미널 본체 `bplus64.exe`, 알림 담당 `wintrv.exe`. 모니터 2대(합쳐서 3840x1080), 터미널은 **왼쪽 모니터** 전체화면.
- **새 알림창 = 별도 창** ✅: 클래스 `BLPMsgWClass`, 프로세스 `wintrv.exe`, 항상 위(topmost), 제목 없음, 크기 약 150x25, 우상단에 `Msg:S. Notificat…` 글자. → 창 목록에서 이 클래스를 찾으면 알림 감지 가능(클릭 없이). 그 창을 **클릭하면 수신함(MSG)이 열린다** ✅
- 터미널 창은 프로그램이 글자를 **자동 복사(UI Automation, Ctrl+A/C)로 뽑을 수는 없다**. 하지만 **화면을 캡처해서 Claude가 눈으로 읽는 것은 된다** ✅ (그래서 본문 스크리닝이 가능). 자동 복사/OCR은 무인화용 대안일 뿐 필수가 아니다.
- **키보드 입력**: SendInput 유니코드 방식은 터미널이 무시한다. **가상키+스캔코드(`keybd_event`)** 방식은 된다 (`term_ops.vk_type`). 명령창 클릭(360,85) → 타이핑 → Enter 로 `SDSK 번호` 이동 확인.
- **티켓에 직접 들어가기**(`SDSK 번호`)는 수신함의 노랑(안 읽음)을 회색으로 바꾸지 않는다 ✅(사용자 표시 보존). 반대로 **수신함 줄을 클릭하면 읽음 처리**된다 → 자동화는 수신함 줄을 클릭하지 않는다.
- **티켓 화면 `AI Summary`(왼쪽 첫 메뉴) = Bloomberg 자체 AI 요약** ✅: 클릭 후 약 10~15초 로딩. 요청 내용/현재 상태/관계자별 정리를 한 화면에 보여줘서 **티켓 한 건을 화면 1장으로 파악**할 수 있다. 단, `Summarized up to:` 시각까지만 반영되므로 그 뒤 최신 글은 Key Details 맨 아래(티켓은 항상 최신 글 위치로 열림)를 같이 본다.
- 설치된 도구: `pywin32`, `uiautomation`, `pillow`, `openpyxl`, `xlwings`, `playwright`. (`pyautogui`, OCR 라이브러리는 없음)
- 코드: `term_ops.py`(클릭/타이핑/휠/캡처/goto), `probe_notify_windows.py`(조사용, 이제 불필요 — 필터가 bplus/blp만 봐서 wintrv 알림은 못 잡았음)

### 7-3. 알림 감지 후 흐름 (2026-10-09 시험 실행으로 검증)
1. `BLPMsgWClass` 창이 보이면 = 새 알림 (또는 아침 첫 실행)

### 7-5. 화면(workbench) 설계 결정과 시안 이력 ✅ (2026-10-09)

**디자인 취향 ✅**: 사용자는 **슬레이트 계열의 연한 톤 + Noto Sans KR + 숫자는 IBM Plex Mono + 얇은 선 + 둥근 작은 태그** 스타일(시안 3·5·6·7·8)을 좋아한다. 현재 workbench의 **주황 표 헤더 + 남색 날짜 배너** 스타일(시안 4)은 "지금은 단순한 디자인이고, 네가 만들어 준 색상·폰트·선이 더 좋다"고 했다. → 티켓 관련 화면은 슬레이트 스타일로 만든다. (실제 `dashboard.html`에 넣을 때 기존 CSS와 충돌하지 않게 클래스 접두사 `tk-` 사용 ⚠)

**거부된 레이아웃 ✅**: 큰 카드형 한 건당 블록(시안 1, "한눈에 확인하기 어렵다"), 날짜별 칸반 칸(시안 2 B), **주간 달력 띠(시안 3, "별로")**, 왼쪽 보기 목록은 "상태가 너무 많다"는 지적과 함께 후순위.

**채택된 방향 ✅**: **한 줄 표**(시안 2의 A) → **오더 칸 전부 + 티켓 칸 2개를 오른쪽에 덧붙인 통합 표**(시안 8, 최신).

**시안 8 구조 (최신, 개선 필요)**
- 위쪽 바: `티켓 칸 보기`(티켓 칸 접기/펼치기), `NEW만 보기`, `NEW 지우기`
- 표: 왼쪽 "오더(SAP)" 10칸 = 현재 보드 칸 그대로(Type, 체크, Order #, Item, M/N, S/N, Customer, Phone, Address, Memo). 오른쪽 "티켓(Bloomberg)" 2칸 = **확인 날짜**, **상황 · 할 일**(+ 담당/참고, Rep, 읽은 글 번호 작은 글씨).
- Order # 칸: 오더번호(굵게) + OBD/ORD(회색) + `SDSK 숫자`(눌러서 복사) + (연결 안 된 줄이면) 연결 번호 입력칸
- 품목이 여러 줄인 오더는 지금 보드처럼 줄이 여러 개이고 Order #/Customer/Phone/Address/Memo/티켓 칸은 줄 묶음(rowspan)
- 날짜 구간 배너: 오더가 있으면 **배송일 기준**, 오더 없는 티켓은 **확인 날짜 기준**, 날짜가 없으면 맨 아래 "날짜 없음". 오늘 해당 구간은 주황 배너.
- 확인 날짜 칸: `오늘 10/9`(주황) / `10/14 D-5`(회색) / `-`. (보라 "확인필요" 배지는 쓰지 않음)
- 모든 칸은 눌러서 바로 수정(상황·할 일·메모·Customer·Phone·Address). Item/M/N/S/N은 SAP 값이라 수정 안 함.

### 12-3. 코드 원칙 (기존 workbench와 꼬이지 않게)
1. **티켓 코드는 `sap_automation/tickets/` 안에만** 둔다. 기존 workbench 파일(`db.py`, `workbench_app.py`, `templates/dashboard/*`) 수정은 보드 연동 시점에 **최소한으로**, 수정 내용은 이 매뉴얼에 기록한다.
2. **DB**: 기존 `orders`(UNIQUE(order_no, delivery_no))에 티켓을 억지로 넣지 않는다. 새 테이블을 따로 둔다 ⚠(제안): `tickets`(키는 `SDSK 숫자` 형식 문자열, 제목/Rep/구분(담당·참고)/확인 날짜+근거/상황/할 일/메모/읽은 글 번호/최신 시각/NEW 여부), `ticket_order_links`(티켓 키 ↔ 오더 번호들, 번호만 적어둔 "대기 연결"도 허용). 오더 테이블은 읽기만 하고 티켓 쪽에서 참조.
3. **티켓번호는 항상 `SDSK 숫자` 문자열**로 저장·표시한다(5-4). 숫자만 쓰지 않는다. (연결 비교용 숫자 추출은 비교 시점에만)
4. **화면**: `dashboard.html`은 `templates/dashboard/01~08_*.js`를 번호순으로 합친다. 티켓 칸은 **새 조각(`09_tickets.js`, 필요하면 별도 CSS 조각)** 으로 추가하고 include 줄만 늘린다. 교훈(2026-08-27): **새 최상위 `const`는 `renderAll()` 첫 호출보다 앞에 둘 것**(안 그러면 보드 전체가 백지). `PAGE_TEMPLATE`은 서버 시작 시 1회 캐싱되므로 화면 파일 수정 후 `/api/workbench/restart` 필요. 수정 후 `check_dashboard.py`(문법 검사) 실행.
5. **읽기와 쓰기를 분리**한다. 쓰기(Add Note, Transfer/재배정, Resolve, 채팅 전송)는 사용자 확인 없이 호출되지 않게 한다.
6. **터미널 조작은 `tickets/term_ops.py`만 거친다.** 좌표는 터미널이 왼쪽 모니터(1920x1080) 전체화면일 때 기준. 키 입력은 `vk_type`(가상키+스캔코드)만 동작. **수신함 줄을 클릭하면 읽음 처리**되므로 클릭 금지(티켓은 명령창 `SDSK 번호`로 이동). SAP 자동화 루프와 **포커스 락을 공유**해야 한다(기존 `focus_guard.py`, `ExcelWriteLock` 패턴 참고).
7. **개인정보**: 엑셀 내보내기, 스크린샷, 실명·전화번호가 든 시안 HTML은 **git에 올리지 않는다.** 시안 원본은 `C:/1/티켓관리/mockups/`에 보관.
8. **매뉴얼을 먼저 고치고 코드를 고친다.** 규칙이 바뀌면 이 문서의 해당 장과 변경 이력을 같이 갱신한다.
